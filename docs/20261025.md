
## FSR and protocol behavior

- FSR is sampled every 5 ms and smoothed with a 0.15 filter coefficient.
- A 2% normalized movement deadband limits jitter; value reports are limited to
  at most one per 20 ms.
- In `mixsense_gr_erm`, more pressure lowers threshold: mapped release corresponds
  to 0 dB, and full mapped pressure corresponds to -60 dB.
- Initial position uses **0x06 CONTROL_SNAPSHOT**. It does not overwrite the host
  parameter. Subsequent movement uses **0x01 CONTROL_VALUE**, threshold ID 0.
- Motor levels use **0x10 HAPTIC_LEVEL**, endpoint 0, through the existing v1 codec.
  The production profile keeps native USB binary-only; UART0 carries separate debug output.
- Packet format and existing control IDs were preserved.

## GR-to-vibration behavior

This is a first bench mapping, not a calibrated perceptual model:

| Measured state | Requested motor drive |
|---|---|
| GR <= 0.5 dB | Off |
| GR above 0.5 dB through 18 dB | Linearly increasing positive RTP, approximately 30..90 |
| GR >= 18 dB | Capped at RTP 90 |
| Input below -90 dBFS, invalid metric or bypass | Zero drive |

The host sends normalized protocol levels; the combined firmware independently
caps positive signed RTP at **90/127**. This is a drive-code limit, not a measured
motor voltage. The minimum perceptible/startup drive still needs calibration.

GR haptics defaults off and requires explicit activation after connecting. It
requires a new audio publication after activation, disarms on serial session changes
or editor close, and is mutually exclusive with the synthetic source. Stop/zero
also disables GR haptics.

Held nonzero output refreshes at 50 ms, with prompt updates when the value changes.
The source expires after **250 ms** without a new publication. The MCU separately
clears output after **1000 ms** without valid haptic commands or on USB session changes.
Pulses are capped at 500 ms and maintain a separate continuous baseline.

Driver configuration/status is checked every 100 ms. Faults latch output off and
require reset; stop writes are retried where the bus can still reach the driver.
Without a wired MCU-controlled EN, an I2C failure cannot guarantee hardware shutdown.
Protocol v1 has no device-readiness or physical-vibration acknowledgement.

## Why the demo showed about 12 dB GR

For a constant detector level above threshold, ratio R gives:

```text
GR = (input_dB - threshold_dB) * (1 - 1/R)
output_dB = input_dB - GR        # before makeup

Input -18 dB, threshold -36 dB, ratio 4:1:
GR = 18 * 0.75 = 13.5 dB
Output = -31.5 dB
```

The demo sine only reaches -18 dBFS at its peaks. This prototype calculates target
reduction from individual sample magnitudes, then smooths GR with attack/release.
With the default 10 ms attack and 100 ms release, its applied reduction settles
around **12.3 dB**. Tests cover both the constant-level 13.5 dB case and the sine case.
The meter displays a positive reduction amount: 12 dB GR means -12 dB of compressor
gain before makeup. A different detector design can produce a different sine reading.

## Driver diagnosis and recovery

The first combined live test changed GR correctly but produced no vibration,
even with the GR-haptics checkbox checked. Diagnostic firmware showed:

```text
Before full power cycle:
DBG ok=0 rx=0 fault=Adafruit_begin_not_detected
REG rd=00 s=00 m=00 f=00 c=00 r=0 b=1

After full USB power cycle, same diagnostic firmware:
DBG ok=1 rx=0 fault=none
REG rd=1F s=E0 m=05 f=36 c=A0 r=0 b=1
```

All five register reads succeeded after power cycling, and the driver was ready
in ERM/RTP mode with zero output. Wiring was left unchanged. This demonstrates
recovery following a power cycle; the underlying electrical/reset cause is **not
isolated**. It is not evidence of a resolved wiring defect or an automatic firmware fix.

RESET alone restarts the ESP32 while leaving the USB-powered driver supplied.
For this setup, **after firmware upload, unplug USB for at least 5 seconds and
reconnect without holding BOOT**. The normal binary-only firmware was restored,
power-cycled, and the user then confirmed the complete FSR/GR/vibration test passed.

The first diagnostic line was too long for the native USB endpoint's transmit
space and was suppressed. Reports were corrected to two alternating lines shorter
than 64 bytes. Debug USB text is restricted to the diagnostic profile.

## Rebuild and run

From the repository root, using a Makefiles build tree:

```sh
cmake -S . -B build -G "Unix Makefiles" -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build build --parallel 4 --target MixSense_Standalone MixSenseCompressorTests MixSenseControllerTests MixSenseUsbTests MixSenseRefinementTests MixSenseSerialPortTests MixSenseMacSerialTests
ctest --test-dir build -C Debug --output-on-failure
open -a "$PWD/build/MixSense_artefacts/Debug/Standalone/MixSense.app"
```

Do not switch generators inside a previously configured build tree.

For the working firmware, with PlatformIO available as `pio`:

```sh
pio run -d firmware/esp32s3 -e mixsense_gr_erm
pio run -d firmware/esp32s3 -e mixsense_gr_erm -t upload --upload-port /dev/cu.usbmodem101
```

Close other serial owners before upload. If the programming port is absent, enter
download mode with BOOT/RESET and select the actual enumerated port. After upload,
perform the full USB power cycle described above and use the runtime port in MixSense.

## Video/demo starting procedure

At the user's request, MixSense was restarted in its default state and a motor-zero
command was sent. The working firmware was preserved; no reflash was needed for
recording preparation. The fresh app starts with test tone and GR haptics off.

1. Connect CDC to `/dev/cu.usbmodem348518B5D36C1` on this Mac.
2. Keep speaker/headphone volume low and enable the test tone.
3. Leave Bypass off, set threshold to about -36 dB for a visible initial response,
   and enable **Enable GR haptics (ERM)**.
4. Vary FSR pressure to demonstrate threshold, GR and vibration changes.
5. Enable Bypass to demonstrate stopping the motor.
6. Disable the test tone and GR haptics when finished.
